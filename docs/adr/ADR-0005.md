# ADR-0005: Historical Correction Semantics

**Date**: 2026-08-22
**Status**: `PROPOSED`
**Governs**: `timonelo.evidence.corrections`

---

## Context

A disagreement between an old value and a new one can mean two different
things. Either the store currently holds two Statements that contradict each
other — a problem needing a human — or a representation was corrected at some
point and we are recording that it happened. Conflating them means either
paging a curator about settled history, or silently filing a live contradiction
as an archived footnote.

`ConflictLog` and `StatementEditor` model the first.
`HistoricalCorrectionLog` models the second, and until now was specified only
by a module docstring.

### Terminology warning

ADR-0002 §5 states *"Corrections are new events, never edits."* That sentence
is about the **append-only evidence event log**: a re-reading is appended as a
new `EvidenceEvent` rather than mutating an old one. It is **not** about
`HistoricalCorrectionLog`. This ADR uses **HistoricalCorrection** exclusively
for the latter. The two mechanisms share a word and nothing else.

---

## Decision

### H1 — A HistoricalCorrection is explicit, never detected

It exists only when a caller invokes `HistoricalCorrectionLog.record()`. No
code path infers one. A non-empty `basis` is mandatory: a correction without a
stated reason is indistinguishable from a guess.

### H2 — A live Conflict requires two Statements

`StatementEditor.create()` records a Conflict only when an existing Statement
shares **entity_id**, **question_id** and **statement_type**, has an
**overlapping validity window** (`validity_overlaps`), and holds a
**disagreeing value** (`values_disagree`, exact inequality — no coercion).

Absent a second Statement, a Conflict is **structurally impossible**. Reporting
zero live conflicts in that situation is arithmetic, not evidence of
cleanliness, and must never be presented as the latter.

### H3 — Neither mechanism touches a lifecycle axis

Recording a HistoricalCorrection mutates no `EvidenceCondition`,
`HumanReviewState`, or `PublishStatus`. Resolving a Conflict records a decision
and likewise mutates none. Axis transitions require explicit lifecycle actions.

### H4 — VALUE_CORRECTED requires a replacement Statement

`CorrectionKind.VALUE_CORRECTED` requires a non-null
`replacement_statement_id`; `record()` raises otherwise. Recording that a value
changed while proving no Statement carries the new one asserts a correction
nothing can answer.

### H5 — An absent prior must be declared

`PriorRepresentation` is mandatory:

- `STATEMENT` — the prior reading was a Statement; `prior_statement_id`
  required.
- `LEGACY_NON_STATEMENT` — the prior reading was never a Statement (e.g. a
  legacy knowledge file); `prior_statement_id` must be absent.

Both mismatches raise. A null prior is a claim about history and must be
stated, never left to inference.

### H6 — ReferenceIntegrity is local metadata, not a truth axis

- `VALIDATED` — references present, all checked against known IDs.
- `UNVALIDATED` — no known-ID sets supplied; nothing was checked.
- `NOTHING_TO_VALIDATE` — checking requested, no references present.

This describes **the correction record's own ID references**. It is **not** a
canonical truth or lifecycle axis, carries no evidential weight, and the
TruthEngine never reads it.

It replaced a boolean that reached its strongest value in its weakest case:
with no statement references, `not any(statement_ids)` was trivially true, so a
record referencing nothing reported "validated". The tri-state exists so
*"nothing was checked"* can never again be read as *"checked"*.

The superseded boolean is **not migrated**. `HistoricalCorrectionLog` refuses
to load a record carrying `references_validated`, because `true` was reachable
from two states that now differ; translating it either way would reinstate the
ambiguity.

### H7 — A correction creates no answerable knowledge

Answerability comes from the replacement Statement, subject to its own axes.
The correction records that the change occurred. A correction is never a source
of truth for the corrected value.

### H8 — The stores are independent

`ConflictLog` and `HistoricalCorrectionLog` are independent mechanisms. Their
coexistence is permitted by the current model: both may exist for the same
entity and question.

**Consumers MUST NOT infer that the presence of one excludes the other.**

This ADR does not introduce mutual-exclusion logic and does not claim
exclusivity. Anyone requiring it must implement and enforce it first.

---

## Consequences

Corrections are audit history and nothing more: invisible to querying,
publication and confidence. A curator wanting the corrected value to be
answerable must author a Statement — H4 makes that mandatory rather than
optional.

`NOTHING_TO_VALIDATE` is currently unreachable for `VALUE_CORRECTED`, since a
replacement is always present. It is retained for future `CorrectionKind`
members and is exercised directly at record level.

## Verification

Every normative clause above was cross-checked against the implementation at
the time of writing.

| Clause | Evidence |
| :--- | :--- |
| H1 | `corrections.py` `record()`; no caller in `src/` besides the module |
| H2 | `editor.py` detection block; `values_disagree`, `validity_overlaps` |
| H3 | `conflicts.py` `resolve()`; test asserting lifecycle axes unchanged |
| H4–H6 | `record()` guards; `tests/test_historical_corrections.py` |
| H7, H8 | `HistoricalCorrectionLog` referenced by no other `src/` module; zero occurrences of "correction" in `engine.py` |

## Out of scope

This ADR deliberately makes no claim about the following. Each is a known,
recorded gap; silence here is intentional, not an oversight.

- **Mutual exclusion** of Conflict and HistoricalCorrection — unenforced.
- **Event admissibility.** At least one ingestion path constructs
  `EvidenceEvent` objects directly rather than through
  `EvidenceEventLog.append()`, bypassing its validation.
- **Question registration.** Unregistered question identifiers remain in use.
- **Statement-type value domains.** `deck.venue_present` in particular is used
  across venue names, deck names on deck entities, and deck-list values. No
  statement_type's value domain is declared settled by this ADR.
- **Confidence.** Corrections contribute nothing to confidence propagation.
- **Migration** of the superseded boolean, beyond explicit refusal.
- **Extension semantics for `CorrectionKind`**, which has one member.
