# ADR-0001: Adopt the Five-Plane Spatial Architecture

---

## Context & Problem Statement

Timonelo previously evaluated a monolithic "Knowledge Pack" model and a subsequent two-pack proposal ("Knowledge Pack" + "Experience Pack"). 

Under rigorous first-principles analysis, both approaches proved flawed:
1. **Conflation of Storage and Epistemology**: A "pack" is a serialized distribution artifact, not an architectural boundary.
2. **Conflation of Mathematics and Sentiment**: Calculating an elevator walking distance ($35\text{m}$) or checking whether a lifeboat intersects a sightline is pure geometric derivation (mathematics), not a human "experience".
3. **Rigid Pre-Computation**: Pre-baking human interpretations (family connections, quietness indexes, step-free access) into static files creates combinatorial storage explosion and prevents dynamic, multi-perspective querying.

To scale across thousands of ships over decades, Timonelo requires an architectural model that cleanly decouples **sensory evidence**, **canonical physical topology**, **mathematical spatial derivations**, **human cognitive perspectives**, and **client presentation**.

---

## Decision

We formally adopt the **Five-Plane Spatial Architecture** as the foundational system design for Timonelo:

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                               THE FIVE-PLANE SPATIAL ARCHITECTURE                                 │
│                                                                                                  │
│   [ PLANE 1: EVIDENCE PLANE ] ────────────────────────────────────────────────────────────────   │
│   Immutable, content-addressed raw sensory records (blueprints, survey photos, manifests).       │
│                                              │                                                   │
│                                              ▼                                                   │
│   [ PLANE 2: SPATIAL ONTOLOGY PLANE ] ────────────────────────────────────────────────────────   │
│   Canonical metric geometry and topological connectivity graphs. Zero opinions.                  │
│                                              │                                                   │
│                                              ▼                                                   │
│   [ PLANE 3: SPATIAL CALCULUS PLANE ] ────────────────────────────────────────────────────────   │
│   Deterministic mathematical derivations (pathfinding, raycasting, vertical intersections).      │
│                                              │                                                   │
│                                              ▼                                                   │
│   [ PLANE 4: CONTEXTUAL LENS PLANE ] ─────────────────────────────────────────────────────────   │
│   Stateless, composable pure functions projecting spatial invariants into human perspective.     │
│                                              │                                                   │
│                                              ▼                                                   │
│   [ PLANE 5: PRESENTATION RUNTIME PLANE ] ───────────────────────────────────────────────────   │
│   Headless viewports rendering dynamic spatial briefings across any client surface.              │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

## Plane Definitions & Responsibilities

### Plane 1: The Evidence Plane
* **Responsibility**: Ingests and stores raw primary source artifacts as cryptographically hashed, immutable records.
* **Characteristics**: Content-addressed (SHA-256), un-interpreted, raw sensory data (General Arrangement drawings, physical survey photographs, builder specifications).
* **Boundary**: Zero geometry extraction. Pure provenance and custodial truth.

### Plane 2: The Spatial Ontology Plane
* **Responsibility**: Defines the canonical physical and topological structure of the vessel.
* **Sub-divisions**:
  1. *Metric Geometry*: Normalized continuous coordinates, bounding polygons, deck elevations, door thresholds.
  2. *Topological Graph*: Discrete circulation connectivity (corridor graph networks, vertical lift cores, stair shafts).
  3. *Structural Semantics*: Invariant physical properties (bulkhead fire ratings, railing materials, power socket matrices).
* **Boundary**: Contains zero human advice, zero subjective classifications, and zero walking times.

### Plane 3: The Spatial Calculus Plane
* **Responsibility**: Executes pure, deterministic mathematical computations over Plane 2.
* **Operations**: Graph traversal (path lengths), Euclidean raycasting (sightlines to horizon), 3D vertical polygon intersection (ceiling and floor sandwich co-location), and solar ephemeris projections.
* **Output**: Spatial Invariants ($Distance = 35.2m$, $Overhead = \text{Venue}_{\text{Buffet}}$, $Obstruction = \text{None}$).
* **Naming Rationale**: Named **Spatial Calculus** rather than *Spatial Reasoning* or *Spatial Analysis* because operations on this plane are closed, formal mathematical derivations that emit single deterministic truths without heuristic inference.

### Plane 4: The Contextual Lens Plane
* **Responsibility**: Evaluates Spatial Calculus Invariants against specific human constraints to produce contextual orientation.
* **Characteristics**: Stateless, composable pure functions mapping spatial facts and traveler profiles into human orientation summaries.
* **Examples**:
  - *Mobility Lens*: Filters circulation graphs for step-free access and elevator dependence.
  - *Acoustic Lens*: Translates vertical ceiling/floor adjacencies into noise exposure indicators without predicting subjective loudness.
  - *Family Lens*: Evaluates adjoining cabin portals and proximity to youth areas.
* **Naming Rationale**: Retained as **Contextual Lens** because it acts as an optical filter: changing the lens changes the human perspective without altering the underlying physical object.

### Plane 5: The Presentation Runtime Plane
* **Responsibility**: Consumes Contextual Lens outputs to render visual, tactile, or programmatic orientation interfaces.
* **Characteristics**: Fully decoupled, headless client runtimes (web surfaces, mobile viewports, local offline caches, spatial immersion canvases, or programmatic APIs).

---

## Alternatives Considered

| Alternative | Core Flaw & Reason for Rejection |
| :--- | :--- |
| **Monolithic Knowledge Pack** | Conflates CAD coordinates with human advice. Altering a text summary forces re-signing the entire physical geometry dataset. |
| **Two Static Packs (Knowledge + Experience)** | Pre-baking human perspectives into static files leads to combinatorial storage explosion across diverse personas (mobility, family, luxury). |
| **Server-Side Graph Database** | Fails in disconnected maritime environments where passengers require complete offline orientation at sea. |
| **Game Engine Scene Graphs** | Lacks multi-source evidence provenance, epistemic uncertainty modeling, and explicit *Unknown* state representations. |

---

## Consequences

### Positive:
- **Zero Epistemic Pollution**: Builder facts (Planes 1–2), mathematical truths (Plane 3), and human interpretations (Plane 4) are strictly decoupled.
- **Dynamic Perspective**: Any number of orthogonal lenses (e.g., family routing, reduced mobility, quietness) execute against the same spatial topology simultaneously.
- **Multi-Decade Conceptual Longevity**: The spatial ontology and calculus remain invariant even if presentation frameworks and runtime devices are entirely replaced.
- **Offline Sovereignty**: The spatial mesh and calculus engine can be cached locally on client hardware, allowing full lens execution with zero network dependency.

### Negative & Trade-offs:
- Requires client runtimes to execute a lightweight spatial evaluation engine rather than simply displaying pre-rendered static text.
- Compilation pipeline requires strict separation between raw geometry parsing and topological graph extraction.

---

## Open Questions

1. *Optimal Serialization of Topological Graphs*: Determining the most compact, zero-overhead binary serialization format for Plane 2 & 3 distribution.
2. *Lens Composition Grammar*: Formalizing the declarative syntax for combining multi-lens queries (e.g., `AccessibilityLens AND FamilyLens`).
